An action firewall for AI agents

Your agent does whatever its model asks for. Razorwire sits in between and checks every tool call against your rules first. Dangerous calls are removed before the agent ever sees them, risky ones wait for a person, and every decision goes into a signed log you can undo from.

The model still asked for it

Razorwire took the call out of the model's reply, so the agent had nothing to run. The note tells the model which rule stopped it, so it can change course instead of trying again.

policy.yaml
# the rule that saved production
- id: no-production-db-drop
  match:
    tool: db_drop
  when: args.database == "production"
  action: deny
  message: Dropping the production database is blocked by policy.

How it works

One line puts it in front of your agent

Point your SDK at Razorwire instead of the provider. Nothing else in your agent changes.

agent.py
from openai import OpenAI

client = OpenAI(base_url="http://127.0.0.1:8080/v1")

Your agent

Runs the tool calls that come back. It holds the real access: databases, payments, email.

⇄

Razorwire

Reads every tool call in the model's reply, checks it against your rules, removes or holds the ones that break them, and logs every decision.

⇄

The model

OpenAI, Groq or any provider with the same API. Decides which tools to call.

  1. Check

    Each tool call is matched against your rules, top to bottom, and the first match decides: allow, deny or review. Rules can read the tool, its arguments, the agent's name and how the run has gone so far.

  2. Decide

    A denied call is removed from the reply, with a note naming the rule. A call under review waits for a person with an admin key. Anything that cannot be checked is blocked.

  3. Record

    Every call and decision goes into an audit log, each line sealed to the one before it, so an edited or deleted line shows. When something that went through was wrong, rollback undoes it.

Features

Brakes, a person in the loop, and an undo button

Rules

Plain YAML you can read

Match a tool by name, test its arguments with a short expression, and allow, deny or hold it. Start in shadow mode to see what would be blocked before anything is.

Loop guard

Stops a stuck agent

Razorwire counts what already happened in the run, such as calls, repeats, streaks and blocks, so a rule can stop an agent that loops or runs over budget.

Approval

Risky calls wait for you

You get a message the moment a call is held, on Slack, Discord, ntfy or your own webhook. Approve or deny from the terminal, or from another computer over https. Every decision says who made it.

Approve later

Nobody there? It waits a week

A call nobody answered in time is parked for 7 days instead of thrown away. Approve it when you are back and it is carried out then. It survives a restart.

Rollback

Undo what already ran

Your rules say how to reverse each tool. Razorwire works out the plan from its signed log, shows it first, and undoes newest first, stopping at the first failure.

Streaming

Replies stay word by word

Text reaches your agent as it arrives. The moment a tool call starts, the rest of the reply is held until the whole of it has been checked.

Undo

Rollback shows its plan first and changes nothing until you add --run. The undo itself is carried out by a small service you run, which holds the real credentials. Every request to it is signed.

Look firstNothing touched
$ razorwire rollback --agent support-bot
3 actions went through, newest first:

db_drop  {"database":"staging"}
  cannot be undone: the policy has no undo recipe for db_drop

grant_role  {"role":"admin","user":"u1"}
  undo: revoke_role {"role":"admin","user":"u1"}

create_ticket  {"title":"refund request"}
  undo: close_ticket {"id":812, …}

Nothing was undone yet.
Then undo2 undone
$ razorwire rollback --agent support-bot --run
cannot undo  db_drop
undone       grant_role     → revoke_role
undone       create_ticket  → close_ticket

Undid 2.

Run it again and both are skipped: already undone.

Security

Built like a security product, because it is one

No software is unbreakable. Razorwire closes the known ways in, blocks whatever it cannot check, and makes tampering visible.

  • A key for every agentAn agent's name comes from its key, so it cannot claim another agent's looser rules. Keys are stored only as hashes.
  • The provider key stays insideAgents hold only a Razorwire key, so they cannot go around Razorwire to the model.
  • Agents cannot approve themselvesAgent keys and admin keys never mix. Approving always takes a person.
  • Fails closedA rule that errors, a reply it cannot read, a held call nobody decided: all blocked.
  • Refuses unsafe setupsIt will not open to the network without keys, or talk to a remote provider over plain http.
  • Small and strictNo unsafe Rust, no crashing on bad input, and keys never appear in a log or on screen.

What it does not do

  • It only sees traffic that goes through it. Your network should stop the agent reaching the provider directly.
  • It checks tool calls in OpenAI-compatible replies. Tools the provider runs itself, such as web search, are not checked.
  • It does what your rules say. Start new rules in shadow mode and read the log first.

Install

One command

The installer downloads the build for your machine and checks it against the release's checksums before installing anything.

macOS and Linux

Terminal
curl -fsSL https://raw.githubusercontent.com/razorwire-dev/razorwire/main/install.sh | sh

Windows

PowerShell
irm https://raw.githubusercontent.com/razorwire-dev/razorwire/main/install.ps1 | iex

Builds for Linux (x86_64, any distribution), macOS (Apple silicon and Intel) and Windows (x86_64). Anywhere else, build it with cargo install --path .

  1. Write a policyStart from the example policy in the repository. razorwire check-policy tells you if it is valid.
  2. Start the proxySet POLICY_FILE and your provider's UPSTREAM_URL, then run razorwire.
  3. Point your agent at itChange the base URL to http://127.0.0.1:8080/v1. Blocked calls start showing up in audit.jsonl.
